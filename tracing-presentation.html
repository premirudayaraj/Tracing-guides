Distributed tracing: the missing foundation

Today a request gets a correlation id at the gateway, and then we lose it. We have the id. We don't have the journey.

The goal: anyone in NA can support any project

Right now, supporting a service means knowing its code, its logs and the people who wrote it. That doesn't scale. To let any engineer support any project, we need two things:

  • Observability: seeing what every service is doing, from one place.
  • Distributed tracing: following a single request through every service it touches.

What a trace is, and why it needs Tempo

A trace is the full record of one request's journey through the system. It's made of spans. A span is one step: one service handling one piece of work, with when it started, how long it took, whether it failed, and the facts it knew at the time.

Every span in the same request shares one trace id. Each service passes that id to the next one in a standard request header (traceparent), alongside our correlation id. Each span also points to its parent, the step that called it. That's how separate services' spans join back into one tree.

Why the database matters

Each service sends its spans on its own, at different moments, from different machines. On their own they're fragments. Tempo is what makes them useful:

  • It collects every span from every service in one place.
  • It assembles them by trace id into one request's full journey.
  • It stores them, so you can look back at a failure from yesterday or last week.
  • It makes them searchable with TraceQL, by correlation id, error code, client id, service or failure.
  • It feeds Grafana: the service map, retry trends and cross-team views on this page are all built from what's in Tempo.
Example

Instrumenting a service without Tempo is like fitting a flight recorder with no memory card. The code creates spans, then they're dropped. The instrumentation and Tempo only pay off together.

Tempo vs Loki

In a monolith, one request lives in one process and writes to one log file, so reading logs works. In microservices, one request crosses many services, and its story is scattered across all of their logs.

Loki

Detailed description only. The full text of one event in one service.

Tempo

The fundamental database for observability:

  • Analytics and user tracking
  • Error detection and bug monitoring
  • Application performance monitoring
  • Where an issue happened, and why

The trace records which span failed (where), a short tag like timeout (how) and the cause (why). All three can be searched.

The log holds one line with the full exception text. You search the trace to find the failure, then read that one log line for depth.

The gap today

  • We have a correlation id at the gateway, but nothing follows the request across services.
  • Every investigation is done through logs.
  • Tempo, the database that makes the rest of this page possible, has no data in it.

We are missing the fundamental base for maintaining an application. We can get by for a while with Grafana AI and log-based monitoring dashboards, but we will eventually lose efficiency.

Three things on every request, always

This is the core of our tracing strategy. Every request carries these three, so any one clue leads back to the full flow.

Correlation id
corr-7f3a9c

Ties the trace, the logs and the client's error response to the same request.

Internal error code
ERR-BIL-0042

Says exactly which failure happened, in one searchable value. Set on hard failures.

Failure message
timeout

A short, readable reason. The full exception text stays in the one error log line.

Start from whatever the client gives you

Early warning from retry trends

Retry counts recorded on spans become a trend line. A rising trend warns you before a call fully fails.

A payment call normally retries 0–1 times. Over a week, the average climbs to 3–4. Nothing has failed yet, but the graph shows it coming, so the dependency gets fixed first.

How to achieve this immediately

Each service gets one Confluence page. It lists every trace the service produces, one row per operation against a dependency, like "call to ledger-service completed" or "Kafka publish completed", with what it means and what it tells you. No reading code, no raw spans.

A TraceQL result shows billing-api failed with retries exhausted (3). Open the billing-api page: the "Call to ledger-service: write entry" row says it posts the charge to the ledger, retries up to 3 times, and a timeout there means ledger-service is slow, not billing. Support knows who to call without opening the code.

Step 1
  • Internal error codes are highly recommended. Every hard failure gets a code that links the trace, the log and the error the client sees.
  • Each team runs the tracing MD guides on its service and pushes to PROD without delay. Having at least some traces goes a long way. Don't worry about missing traces.
  • Traces are lower risk than logs. Setting the same attribute twice overwrites it, so duplication is harmless. The guides forbid creating spans inside loops, so runaway volume is designed out.
  • Tempo is built for very high write volume. Our request volume is small by comparison.
  • Give the Claude skill an API key for our Confluence so it can publish the documentation automatically.
  • The documentation gives a full trace definition for each microservice. Every service gets the same page format, under its product's parent page — one documentation pattern for every service, so anyone can read any service's page.

Step 2
  • Fix traces in later releases where needed.
